OCIC Benchmark · Production Execution Plan · v3

Running the experiment: one unit, a generation stage, four phases

Open Claude in Chrome vs Claude in Chrome, then pre-training (experiential vs expert), then execute_code on the expert arm, then continuation: test rollouts that fork a checkpointed session which already holds the experience in its context window. Every rollout is a detached claude process; the orchestrator (runner.py) owns setup, teardown, and grading around it. Latency is the headline metric, and everything is timed. Scoring is retroactive from artifacts.

ISO

Isolation: two independent layers

OCIC lives in Brave · official CinC lives in Chrome

browser state reset, every rollout · every phase

REAL stores app state in localStorage keyed by app, not by run_id. So state is wiped and re-seeded before each rollout and /finish is asserted empty. Two same-app rollouts cannot share one browser profile concurrently.

clear localStorage → /config → assert 0 diffs → hand tab to agent

filesystem ephemeral sandbox · phase 2/3 only

The experience lives in a frozen master dir. Each rollout gets a throwaway copy as the agent's cwd, with the experience at ./experience/, with no --add-dir, so the only directory in scope is the sandbox itself. A header boundary rule (read only under this directory) keeps it in; the disposable per-rollout copy keeps it from leaking across rollouts. Each rollout's trajectory is audited for filesystem escapes.

$CWD/ experience/ (frozen copy: traces + frames) 3B: analysis.md
Concurrency is bounded by browser profiles, not the filesystem. Phase 1 is parallel because its two systems live in different browsers (Brave vs Chrome). Phases 2 and 3 are OCIC-only, so their rollouts serialize on the one Brave profile; more profiles is the throughput lever if ever needed. Rollout workdirs live outside any git repo so no project context bleeds into the agent.

PHASE 2

Pre-training: EXP-2A experiential vs EXP-2B expert

OCIC only · execute_code forbidden · ephemeral sandbox per rollout

Same unit, same test set; the only change is the environment: each rollout's sandbox carries the frozen experience at ./experience/, and the header tells the agent it exists ("you have prior experience against similar apps in ./experience"). Both arms carry viewable frames, so the comparison isolates the source of experience, not its modality. How the agent uses it is up to the agent.

EXP-2A experiential env (6 own Claude-session traces + frames) → 12 rollouts code forbidden
EXP-2B expert env (6 operator recordings + frames) → 12 rollouts code forbidden

Question: does either pre-training beat the phase-1 cold baseline on correctness and steps/latency, and which source of experience is worth more?

PHASE 3

execute_code: two experiments on the expert arm

EXP-2B is the implicit control (its no-code condition already ran in phase 2)
EXP-3A

Naive execute_code

Expert env, header now permits execute_code ("feel free to use execute_code where it helps"). Tests whether the raw invitation changes behavior and latency. Expect prompt iteration: we inspect traces to confirm it actually uses execute_code before trusting the numbers.

EXP-3B

execute_code + analysis

Same as 3A, plus the compressed analysis of the expert rollouts placed in the sandbox (site nuances, dead ends, pitfalls, key behaviors, design decisions). Tests whether amortized, compressed experience converts execute_code into a real win.

Tracked metric: execute_code usage. Per rollout in 3A/3B we count execute_code calls from the trajectory (and audit zero usage everywhere it is forbidden). Usage count sits next to steps and latency in the results.
PHASE 4

Continuation: EXP-4A experiential-fork vs EXP-4B expert-fork

OCIC · Brave · execute_code never mentioned · every rollout forks one checkpointed session

The shift is in the delivery of experience, not the unit. Phases 2/3 put the agent inside a library: knowledge sits on disk at ./experience/ and the header says "go read it." Phase 4 hands the task to a session that has already been through it: a one-time study session is checkpointed, and every test rollout is a fork of that checkpoint: the experience arrives pre-loaded in the context window, with the study's working directory restored on disk as a secondary channel. Same five-stage unit, same seeds, same grader, same jail; only the origin of the session differs. The two arms differ in how the checkpoint acquired its experience: 4A did the job before (it performed the six train tasks); 4B read the library before (it studied the six expert recordings).

study · once · agent (medium)

EXP-4A study: one session performs all six train tasks

The orchestrator drives the standard unit around a persistent session: per segment it opens a fresh tab, seeds /config, asserts a clean /finish, then resumes the same session (plain --resume, session id verified stable) with a next-task message. The agent is never told it is preparing for anything; it simply completes six tasks back-to-back in one conversation. Its workdir starts empty; each segment is captured and evaluated for the record but nothing is curated: the checkpoint keeps the failures too (this run: 3/6 segments passed). Experience is episodic: actions taken, mistakes made, results seen.

study time = data (37.0 min, 6 segments)
study · once · agent (MAX effort)

EXP-4B study: one session internalizes the expert recordings

Same mounted material as EXP-2B (recordings + frames at ./experience/), but the assignment is to study, not solve: work through every recording action-by-action alongside its frames, reconstruct why each move worked (real vs decorative controls, search/filter mechanics, form flows, gotchas), and cross-check until the apps' behavior is predictable, explicitly told a file summary is not the goal, internalization is. The browser is deliberately never mentioned; cross-checking against the live apps is left to its own discretion (any tabs it opens are counted and closed afterwards). Runs at max effort: depth is bought once and amortized across all twelve forks. Experience is declarative: observed expertise, reconstructed into understanding.

LIMITS

API usage limits and observability

Claude Max 20x · target ≤90% of any window

The budget (researched 2026-07): Max 20x gives a 5-hour rolling window (~1,800 prompts after the 2026 doubling; window starts at the first prompt) plus weekly caps: one across all models and one Sonnet-only. Usage is shared with claude.ai and this orchestrating session.

  • Rollouts run Sonnet: protects the all-model weekly cap the orchestration session draws on.
  • Intra-experiment buffer: fixed pause between rollouts (default 45 s, tunable).
  • Inter-phase buffer: ~10 min between experiments.
  • Reactive throttle handling: claude output is pattern-matched for limit messages; on a hit the runner parses the stated reset time (default 20 min), sleeps, and re-queues the attempt. A throttled attempt is never scored.
  • Headroom policy: pause at the first throttle signal rather than probing the ceiling (the 90% rule).

Following along without burning session tokens:

  • tail -f benchmark/logs/<experiment>_<ts>.log: one readable line per stage: setup ok, claude launched, run done in N min, eval PASS/FAIL, buffer.
  • data/<experiment>/status.json: machine-readable progress (n done / total, outcomes).
  • data/<experiment>/summary.json: end-of-experiment wall-clock + outcomes.

Tracked decisions and caveats:
1. Single rep. Test tasks run ×1 (was ×2); compute constraint. Variance is not averaged out; treat per-task deltas cautiously. 2. Dataset v4 = dashdish × zilloft (fly-unified dropped: intermittent Brave interstitial; networkin dropped earlier: zero hard tasks). dashdish 2e+5m+2h and zilloft 1e+6m+2h, 3 mediums each to train (seeds 716+717; zilloft pinned from v3). Every hard task held out for test; train = 6, test = 12. 3. LLM judge deviation. REAL defaults to gpt-4o for llm_boolean; no OpenAI key on this machine, so the judge runs through claude (sonnet), recorded in each evaluation.json. 4. EXP-1B seed adapter. The official extension has no spawnable server for orchestrator seeding in Chrome; adapter chosen at phase-1 time. 5. Sandbox = the agent's cwd. Phase-2/3 experience is mounted at ./experience/ inside a disposable per-rollout working directory (no --add-dir; nothing else in scope). Confinement is a header boundary rule plus a per-rollout trajectory audit for filesystem escapes and off-app browser use. Experiential experience = Claude Code session traces with image bytes replaced by frame references (build_experiential_env.py); both arms keep viewable frames so the comparison isolates source, not modality. 6. Phase-3 control is EXP-2B; the old standalone no-code batch was removed as redundant. 7. Phase-4 mechanics. Forks only resolve from the study session's own project cwd (verified empirically: cross-cwd fork fails), so every rollout wipes and re-extracts the workdir snapshot at the study's absolute path before forking; independence comes from the immutable checkpoint plus per-rollout restore, not from separate directories. Plain --resume keeps one session id across the 4A study's six segments; --fork-session mints a new id per rollout and never mutates the parent. execute_code has a third posture here: not forbidden (P1/P2), not invited (P3), simply unmentioned: available and audited. The expert study runs at max effort, the single deviation from uniform medium (study only; every fork runs medium). The 4A checkpoint is uncurated: it carries its three failed train segments as-is: authentic experience, not a highlight reel. Forked trajectories embed the study transcript as a prefix; per-rollout metrics are sliced from the fork point (run start) so study turns are never double-counted.
