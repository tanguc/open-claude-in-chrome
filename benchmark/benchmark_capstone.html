OCIC BENCHMARK · POST-FIX CAPSTONE · COLD BASELINES THROUGH PHASE 5 · 2026-07-17

Every way we tried to beat a cold browser agent, and the one that finally did

Thirteen post-fix configurations on the same 12 held-out REAL webclone tasks (dashdish, zilloft), sonnet at medium effort, fresh seeded tab per rollout, deterministic + judged grading. This report walks each arm in order: the three cold baselines, then four ways of delivering prior experience. It asks two questions of each: is it more accurate, and is it faster. The answer is a story about delivery, not knowledge.

2 · Accuracy

And this is one underlying leg property: an arm's latency CV and its turn CV correlate +0.93, a leg that is erratic in time is erratic in path length too.

4 · The mechanism: context weight owns latency

One number explains the entire performance ranking: how many tokens each arm's agent carries per turn. Cold and mounted arms carry ~54-61k (the task + page). The forks carry the whole checkpoint on every turn.

Context carried per turn thousands of tokens, by arm

Context carried per turn. The phase-4 forks (480k, 251k) are 5-9x everything else, not because they reason more, but because the entire study transcript is re-processed on every call. Phase 5's atomic warm-up (5C/5D) cut this to ~92k by keeping only one task of history.

The turn-latency law seconds per turn versus tokens carried

The turn-latency law. Each dot is an arm: context carried per turn vs the resulting per-task time penalty against cold. The line is tight (heavier context, slower). This is why the phase-4 forks lost and why shrinking the checkpoint (P4→P5) recovered almost all of it: the loss was delivery weight, never the knowledge itself.

Once context is divided out: thinking is flat, turns is the only thing that moves

Per-turn latency is context, and that is just transformer physics. So we divided context out and asked what else varies between experiments. There are only two candidates: how much the model generates per turn (its deliberation) and how many turns it takes. Measured on the SDK's real per-task turn count, the answer is clean and a little deflating: thinking per turn barely moves at all, and the only behavioral variable is the step count.

Thinking per turn, by experiment output tokens per turn: nearly flat across every arm

Thinking per turn is not a lever. Every arm generates ~130 to 170 output tokens per turn (a short reasoning span plus the tool call), a spread of about ±7% around cold's ~135. Reading experience (mounts, recipe) leaves it at cold; the forks nudge slightly higher (148, 168), a mild side-effect of having a whole session to reconcile; the warm-up is cold-like (128, 136). Whatever prior experience does, it does not change how much the model deliberates per step. Since total time varies 2.5x while thinking-per-turn holds flat, the time differences cannot be thinking, they are context, confirmed from the other direction.

What does move is the turn count. A recipe or warm-up cuts steps below cold; raw or analysed docs on disk push it up (the agent spends turns reading). But turn count is orthogonal to total time (correlation 0.00): taking fewer turns does not make you faster, because per-turn cost varies more than step count does, and per-turn cost is context. That makes turns a separate axis from latency, a precision axis rather than a speed one, so we give it its own treatment next in Section 5. The one-liner for this section: thinking is flat, context is the cost, and turns is a behavior worth measuring on its own.

5 · Turns taken: the precision axis

Latency is one cost of a browser agent; imprecision is another. Every turn is an action on a live, stateful page, and a wrong action, a filter mis-set, a wrong listing opened, a form half-submitted, has downstream consequences the agent then has to notice and unwind. The most direct path to the answer is also the one with the smallest blast radius. Turn count is our measurable proxy for that path length, and, as Section 4 established, it is independent of latency (correlation 0.00 with time), so a method can make the agent more precise without making it faster, and the two must be judged separately.

How we count turns

A turn is one model step: a single round-trip in which the agent observes the page, reasons, and emits an action (a tool call). We count turns with the Agent SDK's authoritative per-task num_turns, not the raw trajectory length. This matters because the forked warm-up arms (5C, 5D) resume a prior session, so the warm-up's transcript rides in the trajectory and inflates the raw count by ~7 to 8x (versus a steady ~1.5x for every other arm). The same contamination hits every trajectory-derived action count (tool calls, browser calls, steps), so num_turns is the only path-length metric that is clean for these arms. An earlier version of this report used the raw count and drew the wrong conclusion; this section is built on the corrected metric.

Turns versus cold, by method fewer = more direct path (green); more = extra steps (red)

Carrying knowledge in-context shortens the path; making the agent retrieve it from disk lengthens it. The warm-up (5D) runs the most direct route, 26% fewer turns than cold; recipe and even the fork run ~14 to 19% fewer, because the knowledge is already in the window and the agent wastes fewer exploratory moves. The disk mounts go the other way, up to +24%: agentic retrieval is itself navigation, and every file the agent opens is another step that can go wrong. Note the fork here: it takes among the fewest turns (most direct) yet is the slowest arm overall, the clearest proof that precision and speed are different axes.

Turn savings versus task length turns saved vs cold against naive baseline turns; toggle legs

And the path-shortening grows with the task. For the warm-up (5D) the turns saved correlate +0.86 with how many turns the task naively takes; on the longest task in the suite it removes ~28 turns, more than a third of the naive path. Recipe scales the same way (+0.77). The disk mount does the opposite (it adds steps, and tends to add more on longer tasks). So the precision benefit concentrates exactly where the risk is highest: on long, multi-step tasks with the most opportunities for a consequential wrong move. The efficient methods do not just finish in fewer steps, they widen that lead as the task gets longer.

Turn-count distribution, per leg density of each leg's 12 task turn-counts; toggle legs to overlay

Each curve is one leg's path-length distribution across its 12 tasks; toggle legs to compare. The warm-up (5D) sits left and narrow (short, consistent paths), the raw mount (2B) sits right (longer paths), and cold falls in between; the fork is left-of-cold but with a wider spread. Pooled median is 28.5 turns.

6 · Two rankings that disagree: turns vs latency

We now have two efficiency metrics that measure different things: turns (path directness, Section 5) and latency (wall-clock time, Section 3). If they ranked the arms the same way, one would be redundant. They do not. The rank correlation between them is only +0.30 (Spearman), so knowing an arm is turn-efficient tells you almost nothing about whether it is fast. This section puts the two orderings side by side and reads the arms that move.

The reshuffle vertical height is proportional to the actual value (turns left, minutes right); crossings = disagreement

Red lines fall, green lines rise. The story lives in the crossings. 4A, the experiential fork, is the whole point: it takes the 2nd-most-direct path of any arm (rank 2 on turns) yet finishes dead last on latency (rank 13), a plunge of eleven places, because every one of its few, direct turns drags ~365k of context. Efficiency of path and efficiency of time are not the same thing, and the fork is the proof. Mirroring it, 2A, the raw disk mount, rises seven places (rank 9 on turns to rank 2 on latency): it wanders down a long path, but each of those turns is cheap, so the wandering is nearly free. Only 5D sits at rank 1 on both, the one arm that is both the most direct and the fastest.

The same arms in scalar space turns vs minutes; the bottom-left corner is the goal

Ranks flatten magnitude, so here are the raw values, and the arms fall into three groups that the delivery mechanism draws for you. Prompt-embedded (green: recipe and warm-up) clusters in the bottom-left prize corner, few turns and fast, because the knowledge is in the window and costs almost nothing to carry. Cold and on-disk retrieval (blue: the cold legs plus the raw and analysis mounts) sits just to the right, still fast but on a longer path, cheap per turn, yet the agent spends extra steps because it has no in-window guidance or must go read files. In-context forks (red) break away to the top: the context tax strands them there regardless of turn count, 4A lands in the worst corner despite a near-best path. The asymmetry underneath it all: turns span just 1.7x (24 to 40) while latency spans 2.7x (21 to 57 minutes), so being a few turns more direct buys a little, but being context-heavy costs enormously. Only 3D sits outside its family, a mount whose latency was inflated by a single failed hard task. Judge a method on turns and latency separately; a good position on one axis is no guarantee on the other.

7 · Hypotheses, tested

H1 SUPPORTEDOCIC is at least as good as the official extension. Cold OCIC-Brave 11/12 in 23.4m; official CinC (setup-parity) 9/12 in 24.5m; OCIC-Chrome 9/12 in 26.5m. OCIC leads on accuracy and per-action latency (0.12s vs 0.27s median round-trip); whole-task time is a tie under setup parity. The big early gap was an unrepresentative old CinC run plus a setup-parity artifact, both corrected.

H2 REFUTEDMounted prior experience improves a healthy harness. Raw mounts 9/12 and 11/12; analysis mounts 10/12 and 11/12; every mean within ±1 min/task of cold, records near-even. The agent barely opens the files, and the healthy harness leaves nothing for them to fix.

H3 REFUTED (with a mechanism)Forking the experience into context helps. The full forks are the worst arms in the benchmark: 8/12 and 10/12, +2-3 min/task, because each turn re-reads a 250-490k-token prefix. In-context knowledge cut search (fewer turns) but paid an ~8x reading tax on delivery.

H4 SUPPORTED (the corollary)The fork's loss is delivery weight, not the knowledge. Phase 5's atomic warm-up shrank the checkpoint 480k→92k and the fork flipped from worst arm to a tie with cold (11/12, +0.13 min/task). Exactly what the turn-latency law predicts.

H5 SUPPORTED (narrowly)A cheap, non-distracting recipe can beat cold. The recipe alone is a wash (11/12, dead-even) because its fixed reading cost cancels its help on this easy-heavy suite. Combined with the atomic warm-up (5D), it is the first arm faster than cold: 20.9 vs 23.4m, faster on 7/12 tasks, the gains concentrated in the hard tasks, the difficulty effect paying off.

The one-line conclusion. Knowledge never hurt and rarely helped; delivery decided everything. On disk it is ignored (free, useless); forked whole it is a per-turn tax (expensive, harmful); distilled to a recipe plus one task of warm-up it is finally net-positive (5D). And it only shows up on hard tasks , this suite is at ceiling, so the honest headline is a modest time win, not an accuracy breakthrough.

8 · Difficulty is where the wins live

Time benefit versus cold, by task difficulty easy, medium, hard tiers

Mean time benefit vs cold, split by task difficulty, for the arms that ever help. Every positive bar is in the hard tier; easy tasks show flat-to-negative (the fixed cost of any delivery exceeds the tiny task). This is the consistent thread across all phases: prior experience pays in proportion to task difficulty, and this suite has too few hard tasks for it to dominate the totals.

The longer the naive task, the more the winning method pays

Every task carries a baseline latency: what it costs to hand a browser agent the task cold, which grows with the number of turns the task naively takes. The question that matters for continual learning is whether its benefit grows with that baseline. It does, and cleanly.

Time saved versus baseline task length seconds saved vs cold against naive turn count; toggle legs

The prompt-embedded method (5D, warm-up + recipe) saves more the longer the task is (correlation +0.73 between seconds saved and baseline turn count; 5A recipe alone +0.66). On the shortest tasks it is roughly break-even, the fixed cost of carrying the recipe eats the gain, but on the longest task in the suite (zilloft-9, ~69 naive turns) 5D returns ~106 seconds. The fork runs the other way (correlation −0.42): the longer the task, the deeper it sinks, because its per-turn context tax compounds over every additional turn. So the two families diverge with length, prompt-embedded expertise pays off increasingly, in-context history costs increasingly. This suite is only medium-length; the trend lines say the gap widens on anything longer.

Accuracy does not scale, and the dataset is the reason. Every arm lands at 8 to 11 of 12, with cold already at 11/12 and no method exceeding it; the one unsolved task is a broken rubric, not a hard one. The suite sits at its accuracy ceiling, so it can measure latency gains from continual learning but cannot show accuracy gains. Whether these methods lift success on genuinely hard tasks is a question this data leaves open; it would need a harder, un-capped suite to answer.

9 · How each leg scales with difficulty

Difficulty is defined per task as an equal blend of its classification (easy/medium/hard) and its denoised baseline time (the mean run time across the three phase-1 cold legs, averaged to cancel single-run noise), scaled 0–10. Then each leg's per-task time is measured against that same 3-leg baseline, and we ask how that performance moves as difficulty rises.

Difficulty sensitivity does each leg hold up as tasks get harder?

Difficulty sensitivity = the slope of (minutes vs baseline) against difficulty, per leg. Negative (green) = the leg holds up or improves as tasks get harder; positive (red) = it degrades. The picture is unambiguous: the forks are difficulty-fragile (4A +0.44 min per difficulty point, Spearman +0.58; 4B +0.12/+0.44) because their per-turn context tax compounds with the extra turns hard tasks demand. Every recipe / warm-up-recipe leg is flat-to-negative (5D −0.09, 5A/5B ~−0.08): difficulty-robust. Mounts are flat; 3D's lone positive is one catastrophic hard task (zilloft-10), not a trend (Spearman −0.08).

Performance versus difficulty per task and leg, with trends

Each dot is one task at its difficulty (x) against that leg's minutes saved or lost vs the denoised baseline (y, below zero = faster than baseline). Dashed lines are per-leg trends; toggle legs above. The fork trends tilt UP with difficulty (they bleed time on the hard tasks); the recipe and 5D trends stay flat or tilt gently down. The answer to the question: a leg's delivery mechanism decides its difficulty behavior. Carrying knowledge in-context is a tax that grows with difficulty, while a recipe on the page is a fixed near-zero cost that lets its small hard-task savings survive.

Long is not the same as hard: two axes underneath "difficulty"

The blend above leans on time, and time hides a fork in the road. A task can eat minutes because it is long (many routine steps) or because it is cognitively hard (the agent stalls, backtracks, and sometimes fails outright). Those are different problems, and across the suite they turn out to be nearly independent: duration and failure rate correlate just −0.24. Worse for the composite, the time-blended difficulty score tracks duration (+0.67) while staying almost blind to failure (+0.06): it measures how long, not how hard.

Task landscape duration versus failure rate

x = denoised cold duration; y = failure rate across all 22 arms. Dot color is the hand classification (easy / medium / hard). The two axes pull the four hard tasks apart: zilloft-9 is the marathon (longest task, 118 turns, yet fails only 5%: long, not hard), while zilloft-10 is the trap (middling length but fails 32%: the genuinely hard one). Failure is not even confined to the hard label, zilloft-2 and zilloft-5 are medium-classified and fail ~30%. And dashdish-8 sits alone at 100% failure with near-zero duration: not hard, just a broken, judge-random rubric. The time-blend crowns the marathon as "hardest" (score 10.0) and rates the real trap only 6.5. If we want a difficulty axis that predicts failure, it has to be built from failures, not from the clock.

11 · Thematic patterns: how the knowledge is delivered

Set aside the phase numbers and group the arms by their delivery mechanism instead: where the prior knowledge physically lives when the agent runs. Six themes fall out, and they behave as families.

Three patterns unravel once you group this way. One: context weight is the whole story for time (correlation between tokens-per-turn and time-vs-cold is +0.91; against seconds-per-turn, also +0.91). The two disk-mount themes and the recipe theme keep tokens-per-turn near cold (~54–61k) and land near cold time; the forked-session theme balloons to ~365k and pays +27 minutes. Two: neither turns nor thinking is a lever. Turn count sits in a narrow band (25 to 40 across every theme) and correlates 0.00 with time; per-turn thinking is flat too (~130 to 170 output tokens). The warm-up takes the fewest turns (25) and the disk mounts the most (37), yet both land near cold, because what decides time is not how many turns or how hard each thinks, it is how much context each turn drags. Three: accuracy is theme-invariant (9.0 to 11.0 across every family): the delivery mechanism changes what the run costs, not what it can solve. The only two themes that beat cold, recipe and warm-up, are exactly the ones that deliver knowledge without loading the context window.

Where the time goes turns versus per-turn cost, by theme

Each dot is one arm placed by how it spends its time: turns (x) against real seconds per turn (y). Color is the theme. The faint curves are lines of constant per-task time (turns times seconds-per-turn, labeled in per-task minutes), with the cold baseline curve drawn heavier. The vertical axis is what decides the winner: the forks sit near the top (every turn crushed by history) and are stranded on a high-time curve; the warm-up sits just above and to the left of cold, fewer turns but each a touch heavier from its cached prefix, netting a hair below cold's curve; the disk mounts drift right, more turns but light ones, landing right on cold. Nobody wins by taking the fewest or the cheapest turns; the winner is whoever keeps per-turn context lowest. The channel you deliver through, disk or prompt or context, decides the cost far more than the content you deliver.

13 · Methods & integrity

  • Pipeline. Fresh tab → clear → /config seed → clean /finish assert → detached claude -p (sonnet, medium) → gate → byte-exact /finish + trajectory → close → REAL evaluator (jmespath deterministic + sonnet-judged rubric). Forks add a workdir-snapshot restore + --resume --fork-session.
  • Leakage discipline (phase 5). Recipes authored by an ISOLATED Fable-5 agent seeing only the train-derived material; audited against test-set identifiers before use; never edited by the orchestrating session.
  • Known grading noise + the dashdish-8 consistency decision. dashdish-8 is judge-nondeterministic: 5D's carousel answer, identical to what all 13 arms give, re-evaluated 3 pass / 2 fail over 5 runs. Because the rubric's ground-truth answer is the collection rows (which no arm produced) and the judge verdict on the shared answer is a coin flip, we mark dashdish-8 fail for all 13 arms for consistency (original judged verdicts preserved on disk under evaluation_original_judge.json). zilloft-5/10 show the same judge sensitivity (mirage-aware phrasing passes, bare counts fail). The ±2-3 task noise floor applies to every single-run arm.
  • Metrics. tok/turn from per-rollout usage (cache reads + writes + fresh input). first-action = median seconds to the first browser call. All per-task times are run-only, prep excluded. Full statistical treatment (paired permutation, bootstrap CIs, win/loss) is in the archived deep-dive and main reports.
  • Recipe prep attribution (caveat). All recipe variants were authored in ONE isolated Fable-5 session (~8.1 min compute; longer wall clock because it slept on a scheduled wakeup mid-run). The transcript splits into a study/analysis phase (~4.9 min, reading BOTH sources and working out the app mechanics) and a writing phase (~3.2 min). Per-site (5A) and single (5B) recipes are shown with equal prep on purpose: the dominant cost is the shared cross-source analysis, which is incurred whether the output is two site recipes or one combined, so their totals are legitimately near-identical (this is the answer to why they benchmarked the same). The writing phase did touch zilloft more than dashdish and the combined least, but write-op count is a weak proxy for authoring effort, and the difference is marginal, so we do not split the writing per variant. Upstream source-material steps (experiential runs, expert recordings) are shown for full provenance but are a shared, reused cost, not re-incurred per arm. No rollouts were re-run; only the prep accounting changed.
  • Reproduce. python3 analysis/harvest.py && python3 analysis/build_capstone.py. Companion reports: main (studies 1-3) · deep dive (fork forensics, difficulty).
