The levers of guidance
that ocic gives the agent.

Every surface where text or structure flows from open claude in chrome into the model's context. Seven layers — what they are, where they live, what to pull when you want the agent to behave differently.

open claude in chrome · codemode branch · ref dcc8cc7

01at a glance

The model has no privileged view into ocic — it only sees what the MCP protocol surfaces to its host (claude code) and what tool calls return. Every influence ocic has over agent behavior funnels through one of seven layers, listed below from most pervasive to most situational. The illustration shows them stacked: each layer adds its text to the agent's context window, earlier layers carrying more authority by virtue of being present every turn.

L1–L7 · the only places ocic touches the agent's mind

02the seven layers

L1

MCP server instructions field

currently unused · would live in: host/mcp-server.js, host/codemode/server-codemode.js, host/codemode/server-hybrid.js

The MCP protocol's initialize response carries an optional top-level instructions string. Claude Code surfaces this as system-prompt-adjacent context, present from turn one and across every tool call. ocic does not set it today.

best for

Global mode-setting that you want the model to read once and remember — "always call tabs_context_mcp first," "screenshots are stored under imageId," anything that's true regardless of which tool is being invoked.

L2

per-tool description

host/tool-definitions.js

Every entry in tools/list carries a description string the model reads while choosing what to call. This is the workhorse — most agent behavior is steered here.

best for

What the tool does, when to use it, what NOT to use it for, the most common foot-guns. The tabs_close_mcp description explicitly calls out "do not use navigate to about:blank to close a tab" because the model used to default to that workaround.

L3

per-parameter .describe()

host/tool-definitions.js (inside each tool's paramShape)

Every zod field's .describe(...) string becomes a JSON Schema description on that property. Twice-effective: surfaced directly in tools/list AND reflowed as @param JSDoc lines inside the generated TypeScript API block (L4e).

best for

Value-level guidance — required vs. optional, accepted formats, "Tab IDs must be in the current MCP group," etc.

L4

execute_code description

codemode + hybrid variants only · assembled across multiple files

The biggest single lever in the code-mode variants. Composed from six sub-layers, top to bottom in the order the model reads them.

sub contents where
L4a Opening framing + namespace rule (chrome.*) common.js (buildExecuteCodeDescription)
L4b Quick examples (currently two) common.js (same template)
L4c Rules (no setTimeout, no screenshot inside, …) common.js (same template)
L4d "When to use vs. direct tools" — strategy common.js (same template)
L4e Generated TS API block (declare const chrome: {...}) — inherits L2 + L3 tool-definitions.js (generateTsApi)
L4f Per-variant EXTRA_NOTES (codemode mentions screenshot/zoom siblings; hybrid mentions computer sibling) server-codemode.js / server-hybrid.js

editing tip

L4a–d is hand-authored template. L4e is generated from L2 + L3 — sharpening an upstream tool description automatically sharpens the JSDoc inside execute_code too. You only ever write the description in one place.

L5

tool result content text

extension/background.js (per-handler output)

Every successful tool call's return value flows into the model's context as text content. ocic actively shapes these for several tools:

  • tabs_context_mcp → JSON of tabs followed by human-readable "Tab Context:" prose.
  • navigate → "Navigated to X.\n## Pages\n…" markdown.
  • tabs_create_mcp → "Created new tab. Tab ID: N" + context.
  • tabs_close_mcp → "Closed N tab(s)…" + remaining context.
  • read_page → accessibility tree with [ref_X] markers the model learns to reuse.
  • computer({action:"screenshot"}) → image block + imageId the model uses with upload_image.

best for

Teaching the model patterns by what it sees come back. The [ref_X] convention exists only because read_page emits it — once seen, the model writes chrome.computer({action: "left_click", ref: "ref_2"}) on its own.

L6

tool error text

extension/background.js · host/tool-runtime.js

When a tool errors, the string flows back to the model as the result content. ocic produces several distinctive ones, each chosen to make the next call obvious:

  • "Tab X is not in the MCP group." — guards every tab-scoped tool.
  • "Invalid URL: '…'. Could not parse as a valid URL." — navigate.
  • "Could not resolve ref '…' to coordinates." — computer.
  • "Sandbox unavailable: …" / "Sandbox not ready after 30s — retry shortly." — execute_code lifecycle.
  • "Browser extension is not connected." — tool-runtime transport.

best for

Giving the model an actionable recovery path. A good error names what the model should do next — vague errors burn a turn on diagnosis.

L7

per-call execute_code metadata

host/codemode/common.js (packExecuteResult) · host/codemode/worker/worker.js

Codemode + hybrid prepend two lines to every execute_code result:

Execution: 1650ms
Tool calls (4): tabs_context_mcp (12ms), navigate (627ms), computer (1004ms), get_page_text (5ms)
Result:
…

best for

A feedback loop on the model's own batching strategy. The model can see which inner call dragged the batch down and self-correct on the next one — without needing description guidance to explain how to interpret the numbers.

04what is not a lever

Worth knowing what you can't touch, so you don't spend time looking for it:

  • The system prompt. Claude Code controls it. ocic has no hook into it.
  • The user's conversation history. Out of reach.
  • Tool ordering in tools/list. The model picks by name and description, not list position.
  • JSON Schema fields other than description. format, pattern, and examples are technically in the schema, but most MCP clients don't surface them prominently to the model.

05where the biggest swings live

If you have an hour, this is the order of impact:

biggest swings

L4a — the framing + namespace rule. One bad line here sends the model writing computer(…) instead of chrome.computer(…) and you lose minutes per session.

L4d — strategy guidance. Tells the model when to reach for execute_code vs. direct tools. The single biggest determinant of whether code-mode actually wins on a task.

L1 (if you start using it). The only layer present every turn unconditionally. Cheapest place to install a single sentence the model needs to never forget.

L5 — result shape. Surprisingly outsized effect because the model reads it every successful call. Tweak the wording of tabs_context_mcp and you change how the model thinks about tabs.
