Imitation learning for browser agents

Record an expert doing a browser task in two synchronized tracks, what they did and why, across every tab, with reliability guarantees. Hand the trace to a live Claude Code session with zero juggling. Claude learns the task from one rollout and carries out a sister task on its own.

Legend: SEB your instruction  MY CALL a decision you delegated  TESTED resolved by an experiment (§13)  RESEARCH from the rrweb / session-replay study  OPEN needs you.

Draft 3: everything you dictated is folded in and the two uncertain systems (transcription, transport) plus two new ones (HTML-capture cost, channel-connection feedback) are resolved by live experiments. One insight reshaped the architecture: the offscreen document that holds the mic is also the durable buffer that makes long recordings survivable, because the MV3 service worker cannot. Details in §5 and §13.

2Two tracks, never one merged sequence SEB CORRECTION

Draft 2 rendered the demo as a single merge-sorted sequence. SEB caught it: behavior and speech overlap heavily (you talk while you act), so collapsing them into one ordered list loses information. The model is two parallel arrays sharing one epoch clock, rendered as two lanes, never flattened.

// trace.json — two tracks, one clock. NOT one merged array.
{
  "started_at": 1751990400000,           // epoch ms; the shared zero
  "behavior": [                          // Track A — can overlap Track B freely
    { "t": 900,  "tab": 3, "frame": 0, "action": "mouse_move", ... },
    { "t": 2100, "tab": 3, "frame": 0, "action": "left_click", "anchor": {...}, "effect": {...} }
  ],
  "cognitive": [                         // Track B — independent timeline
    { "t": 0,    "end": 2840, "text": "Okay, I'm clicking the New Project button now." },
    { "t": 3160, "end": 4800, "text": "I'm doing this because we always start from the Projects tab." }
  ]
}

Overlap is the norm: at t=2100 you click while the t=0–2840 utterance is still playing. A merged list would have to pick an order; two tracks keep the truth. A viewer aligns them on the clock; the agent reads both.

3Reliability: the guarantee ladder SEB

SEB A lost recording is a disaster. Different parts get different guarantees; state them honestly and design to them.

Behavior
100% · local only
Events stream to IndexedDB as they happen, in the offscreen doc. No network dependency. Survives service-worker death and browser crash up to the last flushed event.
Audio (.webm)
~90% · local only
MediaRecorder with a timeslice writes an audio chunk to disk every few seconds. Crash at minute 9 → minutes 0–8.5 are on disk. The ~10% at risk is only the final un-flushed slice.
Transcript
reliable · needs internet
Produced at stop-time from the saved audio via OpenAI (§5). If offline or the API fails, the .webm is still saved and transcription is retried later. Never blocks the bundle.

SEB After you stop, the extension tells you the state of the recording and whether Claude was notified. That feedback is §4. The ordering rule: persist to disk first, transcribe second, notify third — each stage independent, a later failure never destroys an earlier guarantee.

4Transport + connection feedback RESOLVED

Decided: the OCIC MCP server becomes a two-way channel. On stop it fires recording_complete, which auto-injects into the live Claude Code session (§13-B). The extension shows one of three connection states after you stop, because the server cannot passively know if a channel is live (§13-A) — so we confirm with an ack.

The cheap part: OCIC's MCP server is already a stdio subprocess Claude Code spawns, which is exactly what a channel is. Three changes: declare experimental:{'claude/channel':{}} in server-hybrid.js; fire server.notification() when recording_complete arrives upstream; add that upstream message type on the existing extension→native-host→TCP path.

Why three states, and how we know which

TESTED §13-A Claude Code advertises identical MCP capabilities whether or not it was launched as a channel, so the server can't detect channel-mode from the handshake. TESTED §13-B But a two-way ack works: the server's instructions tell Claude to call recording_ack on receipt, and the ack round-trips. Combining the ack with OCIC's existing native-host heartbeat gives three honest states:

What the extension showsHow it knows
Saved. No Claude Code session connected.Native-host heartbeat is dead → no live session using OCIC at all.
Saved. Sent to Claude, delivery not confirmed.
(channel likely not enabled)		Heartbeat alive, notification fired, but no recording_ack within ~12s.
Saved and delivered to Claude Code.recording_ack round-tripped with the recording id.

All three come after the bundle is on disk. The recording is never contingent on the channel; the channel is a delivery convenience layered on a reliable local save. MY CALL reverse path (Claude→OCIC) stays deferred; the ack tool is the only two-way piece v1 needs.

6What we capture per action TESTED RESEARCH

SEB Know what component you're on when clicking/hovering/typing. Whole HTML or just the component? And how much, without oversaturating the model or the disk? Two inputs answer it.

Decided: per action, store a durable semantic anchor (resolved selector + role + accessible name + visible text + key attributes) plus a pre/post DOM-effect summary. Not full HTML. Screenshots are a throttled visual aid, not per-action.

TESTED §13-E The cost argument is decisive. On real 300KB DOMs:

Per-action capture strategyCostVerdict
Full document HTML~75,000–87,000 tokensOne action blows the context window. No.
Cleaned HTML (strip script/style/svg)~41,000–70,000 tokensStill absurd. No.
Ancestor-path + element (cleaned tags: id/class/role/aria/data-testid)~150–300 tokensThis. Says exactly what and where.
Target element outerHTML alone~30–50 tokensAdd the ancestor path for location context.

RESEARCH The rrweb study refines the "what" and hands us the "effect":

  • Anchors, not node ids. Session-replay tools tag elements with ephemeral per-session integer ids that mean nothing to an agent later. We resolve each target to a durable anchor at capture time (selector + role + accessible name + text). OCIC's content.js already builds most of this descriptor.
  • The effect is the lesson. The DOM mutations right after a click (the mini-cart appears, the filter applies) are the action→result signal an agent learns from. Capture a compact pre/post effect summary per action via a scoped MutationObserver, not a full snapshot.
  • Screenshots stay optional. Session replay deliberately avoids per-frame images because the serialized DOM carries the state. We follow suit: rich cheap text per action, screenshots throttled as a visual aid keyed to steps. This directly answers your "don't overblow the model with a screenshot per action."

Q7 the exact screenshot cadence (every N seconds? on tab switch + major mutation? only when narrating?) is worth one experiment once the recorder exists; the default is "sparse, event-anchored."

7Cross-tab capture architecture RESEARCH

SEB The recording persists across tabs. RESEARCH This is the one capability a page-embedded analytics script structurally cannot have, and an extension can. It's also net-new code we own. The obstacles and our answers:

ObstacleOur answer
The MV3 service worker can't hold the buffer — it dies after 30s idle, caps at 5 min, loses memory. A 10-min recording outlives it.Buffer in the offscreen document (persistent, has DOM + storage), the same one holding the mic. SW is a thin message router only. This is the architecture-shaping insight.
N independent capture contexts — every tab/frame numbers its own DOM nodes from 1; they're unrelated.Namespace every event by (tabId, frameId). Resolve to durable anchors before events leave the content script, so downstream never sees the local ids.
No shared clock — each frame's performance.now() has a different origin.Stamp every event with Date.now() (epoch) at emit. That epoch is the trace's single clock (§2).
"Which tab is active" isn't in the DOMThe SW emits segmentation events from chrome.tabs.onActivated / visibilitychange: "left tab A, acted in tab B, returned." Tabs opened/closed mid-session splice in and out.
Cross-origin iframes break page-embedded replay (postMessage bridge, lost events).We win here: all_frames:true content scripts are already inside every frame, reporting straight to the SW. No bridge, no lost events.
Session-replay comparison: what we borrow vs leave (rrweb / PostHog)

rrweb (which powers PostHog, Sentry, Highlight) is a DOM-serialization + delta-log engine, not a video recorder: one keyframe snapshot of the serialized DOM plus a stream of typed mutation/input/mouse deltas. That's why 10-minute recordings stay small. We borrow the capture technique and leave the replay-for-humans shape.

ConcernBorrowLeave / invert
DOM captureSerialize-to-JSON, input-value-as-attribute, MutationObserver deltas with added/moved/dropped dedup—
Node identityThe concept of resolving an event's targetEphemeral integer ids are useless downstream — resolve to durable selector+role+name at capture time
Volume controlSampling (input:'last', scroll throttle, mouse-move off), deflate packingPostHog's Kafka/S3/ClickHouse pipeline is overkill; we write IndexedDB → bundle
MaskingThe selector/class + maskFn machineryInvert the default to OFF — masked text is exactly the training signal (§8)
SemanticsSerialized attributes give role/aria/nameBuild the step-log IR (anchor + action + effect); rrweb has no notion of a "step"
ScreenshotsTheir instinct to avoid per-frame imagesKeep them optional, keyed to steps

Q8 build-vs-fork: do we vendor a trimmed rrweb as the capture substrate, or write a lean purpose-built capturer (anchors + effect windows only)? Leaning purpose-built — we need ~40% of rrweb and want anchors it doesn't compute. Decide at implementation.

8Mask / override mode SHIP IT RESEARCH

SEB Ship the pretend-action feature; call it override mode (or mask mode). Hold a modifier, "click" without the click firing, so you can demonstrate intent without side effects.

MY CALL Modifier is Alt/Option (fn is invisible to the page; ctrl/shift collide with normal browsing). A capture-phase listener in content.js calls preventDefault()+stopPropagation() while held and tags the event suppressed:true in Track A. RESEARCH reinforces why the schema must carry this flag from day one: session-replay's userTriggeredOnInput distinction is the same idea, and its masking default is the opposite of ours — our capture is unmasked by default because the labels and values are the training signal; override mode is the opt-in suppression, not the default.

9Extension UX SEB

  • Icon = start/stop toggle. Clicking the toolbar icon starts a recording; clicking again stops. This is non-negotiable and not traded for anything else. (Needs an action in the manifest; there is none today.)
  • Settings / sessions page holds everything else: the OpenAI API key (required + validated before the first recording can start), and a sessions viewer.
  • Sessions viewer with progressive disclosure. Primarily so you can verify we store the right thing. All data is visible, nothing hidden: start at session metadata, click deeper into the two tracks, deeper into per-action anchors and the HTML snippets. Overwhelming if flat, so it's disclosed in layers.
  • Multi-user. OCIC is for other people, so no reliance on your machine. Key lives in extension storage, entered in settings.

10Cadence: event-driven SEB

SEB Cadence is dictated by input, behavioral or cognitive. No input → nothing to record (the user may just be waiting; that's fine, it shows as a gap in the timeline). Lots of movement + talking → higher capture rate. RESEARCH This is exactly rrweb's model: capture is triggered by events (mutations, interactions, input), throttled per type (mouse-move sampled, input coalesced to final value), never a fixed frame clock. A quiet stretch is simply an absence of events between two timestamps.

11Bundle format + versioned schema SEB

  • JSON only. No TOON. SEB the token savings don't outweigh the complexity.
  • No prompt.md. The prompt changes more often than the data structure. Instead, the notification carries versioned schema metadata (v0) describing how the contents work, how they relate, and what they cover. v0 is meant to be near-permanent.
  • The notification body is dead simple — "a recording is here" — with the path. All the how-it-works lives in the versioned schema descriptor, not in prose that rots.
// the channel notification payload
{
  "content": "Recording ready: 94s across 2 tabs on linear.app.",   // dead simple
  "meta": {
    "event": "recording_complete",
    "recording_id": "rec_a1b2c3",
    "path": "~/.config/open-claude-in-chrome/recordings/2026-07-08T21-00-00",
    "schema": "v0"                         // points to the frozen structure descriptor
  }
}

Bundle on disk: trace.json (two tracks), audio.webm, screenshots/, SCHEMA_v0.md (the frozen descriptor), meta.json. Location: ~/.config/open-claude-in-chrome/recordings/<ts>/ SEB confirmed good.

12The implied complement: execute_code SEB · keep in mind

SEB This is the complement to execute_code. The rollout provides everything needed to compose one robust execute_code call that runs the whole workflow: the anchors give durable selectors, the effect windows give the expected post-conditions to assert between steps, the narration gives the why. We learn the exact shape when we do the imitation learning, but the recorder should be built knowing its output feeds a single batched call, not just step-by-step replay.
